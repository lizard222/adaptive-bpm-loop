## 1. Автоматические смоук-тесты (запускать из корня `adaptive-bpm-loop`)

Каждый тест — независимая проверка одного модуля/слоя, с собственным счётчиком PASS/FAIL. Все должны заканчиваться `N/N`.

| Команда | Что проверяет |
|---|---|
| `python -m orchestrator.smoke_test` | Оркестратор: старт/тик/завершение экземпляра, сериализация состояния в PostgreSQL (9/9) |
| `python -m eventlog.smoke_test` | Экспорт журнала событий в XES, round-trip через pm4py (5/5) |
| `python -m agents.smoke_test` | Планировщик + Контролёр: запуск экземпляра, напоминание, эскалация, доставка уведомлений (6/6) |
| `python -m simgen.smoke_test` | Генератор синтетических журналов: воспроизводимость по seed (4/4) |
| `python -m agents.second_process_smoke_test` | Второй демо-процесс (`workload_planning`) подключается только конфигурацией; параллельные предложения корректировок по разным контрольным точкам не путаются (7/7) |
| `python -m mining.smoke_test` | Конвейер анализа: conformance checking + временной срез по контрольным точкам (6/6) |
| `python -m mining.corrections_smoke_test` | Алгоритм «расхождения → корректировки»: классификация, пороги, отсутствие ложных срабатываний (6/6) |
| `python -m agents.analyst_adapter_smoke_test` | Аналитик-Адаптер: propose → accept/reject через настоящий FIPA-обмен, режим `auto` (16/16) |
| `python -m agents.params_flow_smoke_test` | Контур адаптации в живой МАС: Планировщик реально читает `process_params_current`, оба агента принимают уведомление о новой версии (6/6) |
| `python -m agents.templater_smoke_test` | Шаблонизатор: полный/неполный контекст, FIPA Request Interaction Protocol (9/9) |
| `python -m agents.interface_flow_smoke_test` | Интерфейсный агент + весь REST-слой заодно: propose → REST → decide → accept-proposal → применение (14/14) |
| `python -m agents.vkr_defense_smoke_test` | Реальная модель «Защита ВКР»: две контрольные точки с параметризованными таймерами, параллельные предложения (7/7) |
| `python -m experiment.smoke_test` | Эксперимент (уменьшённый масштаб): baseline vs adaptive, сходимость по seed (8/8) |

Быстрый прогон всех разом:
```bash
for m in orchestrator.smoke_test eventlog.smoke_test agents.smoke_test simgen.smoke_test \
         agents.second_process_smoke_test mining.smoke_test mining.corrections_smoke_test \
         agents.analyst_adapter_smoke_test agents.params_flow_smoke_test agents.templater_smoke_test \
         agents.interface_flow_smoke_test agents.vkr_defense_smoke_test experiment.smoke_test; do
  echo "=== $m ==="; python -m "$m" 2>&1 | tail -3
done
```

⏸️ **Не входит в этот список**: `experiment.run_experiment` на полном масштабе (`--cycles 8 --seeds 5`, ~65–70 мин) и анализ чувствительности (T-52) — сознательно отложены на конец работы над экспериментом, см. README «Оставшиеся задачи».

## 2. REST API вручную (curl)

Получить токен под нужной ролью:
```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:8000/auth/token \
  -d "username=dept_head&password=dept_head" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  | python -c "import sys,json;print(json.load(sys.stdin)['access_token'])")
```

| Проверка | Команда | Ожидаемо |
|---|---|---|
| Профиль | `curl -s http://127.0.0.1:8000/me -H "Authorization: Bearer $TOKEN"` | роль/имя корректны |
| Список процессов для запуска | `curl -s http://127.0.0.1:8000/processes -H "..."` | `vkr_defense` в списке |
| Ручной запуск | `curl -s -X POST http://127.0.0.1:8000/processes/vkr_defense/launch -H "..." -d "{}"` | новый `case_id`, повторный вызов — другой `case_id` |
| Неизвестный процесс | `POST /processes/unknown/launch` | 404 |
| Запуск не той ролью | тот же запрос токеном `normcontrol` | 403 |
| Задачи | `GET /tasks` | все READY-задачи, включая только что созданный экземпляр |
| Завершение задачи | `POST /tasks/{case_id}/{task_name}/complete` | 200, задача пропадает из `/tasks` |
| Несуществующий экземпляр | `POST /tasks/no-such-id/xxx/complete` | 404 |
| Задача не READY | повторный вызов того же complete | 409 |
| Дашборд | `GET /dashboard/summary` | новый экземпляр виден в `processes`, агенты с `last_active` |
| Корректировки (только dept_head/admin) | `GET /corrections/pending` токеном `secretary` | 403 |
| Решение уже решённого | `POST /corrections/{id}/decide` дважды подряд | второй раз 409 |
| Шаблоны документов | `GET /documents/templates` | `vkr_admission_order` с полным списком `required_fields` |
| Генерация с неполным контекстом | `POST /documents/generate` без обязательных полей | 422, `{"missing_fields": [...]}`, файл НЕ создан |
| Генерация с полным контекстом | то же с валидным `context` | 200, запись появляется в `GET /documents` |
| Скачивание | `GET /documents/{id}/download` | бинарный `.docx`, открывается |
| Несуществующий документ | `GET /documents/999999/download` | 404 |
| Без токена | любой защищённый эндпоинт без заголовка | 401 |

## 3. UI — сквозной сценарий по ролям

Открыть [http://localhost:5173](http://localhost:5173). Проверять в обеих темах (переключатель внизу сайдбара) хотя бы один раз за проход.

### 3.1 dept_head / dept_head
- [ ] «Обзор»: KPI-плашки не пустые, «Ожидают решения» кликабельна и ведёт в «Корректировки»
- [ ] «Процессы» → «Запустить процесс» → `vkr_defense` → тост с `case_id`, счётчик активных вырос после обновления
- [ ] Развернуть строку `vkr_defense` — таблица контрольных точек не падает, если анализа ещё нет — честно «нет анализа»
- [ ] «Корректировки» видны в меню; если список пуст — «Нет предложений»; если есть — «Принять»/«Отклонить» открывают диалог подтверждения, после решения элемент пропадает из списка и появляется в «Обзоре» → «Последние решения»
- [ ] Переключить тему — все экраны читаемы в обеих

### 3.2 secretary / secretary
- [ ] «Задачи»: видит READY-задачи всех процессов (не только своих). **Важно**: список динамический — как только вы завершаете задачу, экземпляр продвигается к следующему шагу, и он тут же становится READY (то есть появляется в том же списке). Это ожидаемое поведение движка, не баг — не пугайтесь, если список выглядит иначе после каждого действия
- [ ] Завершает `approve_topics` созданного в 3.1 экземпляра → диалог подтверждения → тост → задача пропадает
- [ ] «Документы»: генерирует `vkr_admission_order` с валидными полями → появляется в списке → «Скачать» реально скачивает файл
- [ ] Попытка сгенерировать с пустыми обязательными полями → ошибка с точным списком недостающих, без создания записи
- [ ] Пункта «Корректировки» в меню нет

### 3.3 normcontrol / normcontrol
- [ ] «Задачи»: видит **только** задачи `normcontrol` (если экземпляр уже прошёл `approve_topics`) — никаких `admission_order`/`defense`/чужих `approve_topics`
- [ ] Если подходящих задач нет — «Нет активных READY-задач», а не ошибка
- [ ] Завершает свою задачу → экземпляр переходит к `admission_order` (проверить под `secretary`)
- [ ] Пункта «Корректировки» в меню нет

### 3.4 supervisor / supervisor
- [ ] Пункта «Корректировки» в меню **нет вообще** (не просто заблокированный контент)
- [ ] Остальные экраны (Обзор/Процессы/Задачи/Документы) открываются нормально

### 3.5 admin / admin
- [ ] Доступ идентичен `dept_head` (видит и решает корректировки)

### 3.6 Общие проверки состояний
- [ ] Разлогиниться и зайти с неверным паролем — понятное сообщение об ошибке, не «белый экран»
- [ ] На экране «Задачи»/«Документы»/«Корректировки» нажать «Обновить» — список действительно перезапрашивается (не кешируется молча)
- [ ] Отключить backend (`Ctrl+C` на uvicorn) и обновить любой экран данных — должно показать ошибку с кнопкой «Повторить», а не зависнуть на скелетоне загрузки

## 4. Контур адаптации целиком (не только UI)

Ручная проверка, что «журнал → анализ → предложение → решение → новая версия» действительно работает по кругу. **На реальном `vkr_defense`** (норматив в днях) эскалации сами по себе не накопятся за время одной сессии тестирования — для быстрой проверки см. раздел 5.

1. Запустить несколько экземпляров `vkr_defense` (ручной запуск через UI или API, 10–20 раз) и намеренно НЕ выполнять часть задач вовремя, чтобы накопились эскалации (либо переиспользовать смоук-тест `agents.vkr_defense_smoke_test`, который уже это делает синтетически).
2. Запустить анализ: `python -m agents.run_analysis_cycle --process-key vkr_defense` (реальный `InterfaceAgent`, не заглушка — предложение попадёт в настоящую `pending_decisions`).
3. Проверить, что предложение появилось в `GET /corrections/pending` и в UI.
4. Принять его как `dept_head` **в течение `--wait-seconds` (по умолчанию 300 сек)** — иначе скрипт отключится, не дождавшись вашего решения, и корректировка останется помеченной «принято», но реально не применится (см. «Найденные и исправленные баги»).
5. Проверить `GET /dashboard/summary` → `processes[].params.version` — должна вырасти на 1, `reminder_days`/`escalation_days` — измениться согласно типу корректировки.
6. Запустить новый экземпляр (ручной запуск, п.1) и убедиться, что таймеры у него уже используют обновлённые параметры (`GET /tasks` → `due_at`/`remind_at` пересчитаны).

## 5. Быстрый сценарий (минуты вместо дней)

Для интерактивной проверки без ожидания реальных 7–14 дней — тестовая модель `vkr_defense_fast` (`kind="test"` в реестре, не засоряет «боевой» дашборд): те же шаги, что у `vkr_defense`, но таймеры в МИНУТАХ (по умолчанию: напоминание — 1 мин, эскалация — 2 мин после того, как шаг стал READY).

**Обязательное условие**: backend должен быть запущен как обычно (`uvicorn api.main:app`) — с версии E11 внутри него крутится фоновый цикл (`api/background.py`), который сам проверяет таймеры каждые 15 сек. Без него таймеры (в том числе боевые, дневные) не сработают вообще никогда — это не особенность быстрой модели, а общее свойство системы.

1. Запустить: `POST /processes/vkr_defense_fast/launch` (или через UI — в выпадающем списке «Процесс» на «Процессах» он подписан «(тест, быстрые таймеры)»).
2. Ничего не делать 60–90 секунд — не завершать задачу `approve_topics`.
3. Проверить `GET /tasks` или журнал (`docker compose exec postgres psql ... event_log`) — должно появиться `remind_topics` (~через минуту), затем `escalate_topics` (~через 2 минуты), с реальными текущими метками времени. Проверено (19.09.2026): реально сработало само по себе за 90 сек, без единого ручного вызова tick — только фоновый цикл.
4. Прогнать анализ: `python -m agents.run_analysis_cycle --process-key vkr_defense_fast` — увидите реальную эскалацию и, скорее всего, предложенную корректировку в течение секунд, а не дней.

## Найденные и исправленные баги (для истории)

- **19.09.2026** — процесс, у которого ВСЕ экземпляры завершились и ни разу не запускался анализ (нет своей строки в `process_params_current`/`analysis_reports`), полностью пропадал из «Процессы» — дашборд строил список только из активных/параметров/отчётов, без учёта завершённых экземпляров. Найдено при ручном прохождении этого же чек-листа. Исправлено в `api/dashboard.py` (добавлен подсчёт `completed_instances`, список теперь сортируется активные→завершённые→алфавит).
- **19.09.2026** — кнопки «Обновить»/«Запустить новый экземпляр» не сбрасывали страницу пагинации: запущенный на странице 3+ процесс появлялся на странице 1 (сортировка «активные сначала»), а пользователь его не видел. Исправлено — оба действия сбрасывают на страницу 1.
- **19.09.2026** — `Orchestrator.tick_all()` без фильтра по `process_key` тикал вообще все активные экземпляры в базе; `simgen.run_cycle`, вызывая его под `freeze_time(...)`, случайно продвинул несвязанные живые экземпляры `vkr_defense` под симулированным временем — 4 экземпляра получили реальные эскалации с датой из будущего (`2026-10-04`). Исправлено (`tick_all(process_key=...)`), затронутые экземпляры удалены из `process_instances`; событий в неизменяемом `event_log` это не коснулось — для честного пересчёта используйте `--exclude-case-id`.
- **19.09.2026** — как следствие: корректировка, принятая пользователем в UI, не применилась, потому что `agents/run_analysis_cycle.py` ждал ответа всего 8 секунд, а решение пришло позже. Исправлено — `--wait-seconds` по умолчанию 300, плюс уникальный JID на каждый запуск скрипта.
- **19.09.2026** — обнаружено, что живая система вообще никогда не проверяет таймеры BPMN сама по себе (ничего не вызывало `tick()`/`tick_all()` в REST-пути). Закрыто фоновым циклом в `api/background.py` (см. раздел 5).

## Известные ограничения (не баги, если увидите — это ожидаемо)

- Даты у Контролёра/агентов на «Обзоре» иногда «из будущего» — это синтетические данные старых прогонов под управляемым временем (`freezegun`), не реальная активность.
- Контролёр не расширяет контрольные точки динамически из корректировок `add_checkpoint` (T-25, не сделано).
- `workload_planning` нельзя запустить вручную через UI — реестр ручного запуска (`orchestrator/process_registry.py`) содержит только `vkr_defense`.
- Роль `student` объявлена в системе, но демо-входа для неё нет.
