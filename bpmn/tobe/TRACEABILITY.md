# Трассировка «каталог кафедры → to-be модель «Защита ВКР»» (T-22)

> СГЕНЕРИРОВАНО `bpmn/tobe/build_tobe.py` вместе с `vkr_defense_tobe.bpmn` — таблица и модель
> из одного источника и не расходятся. Источник мероприятий — «Бизнес-процессы кафедры
> САПРиПК (версия 3.0)», таблицы БПБак.ВРБ и БПМаг.МД. **Номера ВРБ.01–24 и МД.01–26 назначены
> по порядку строк каталога**: у шифров в каталоге номеров нет.

## Структура модели

- **Уровень выпуска** (процесс `vkr_defense_tobe`): темы, приказы, ГЭК, консультации, график и
  организация защит, отчёт, трудоустройство, архив.
- **Уровень студента** (многоэкземплярный подпроцесс `student_vkr`, по одному экземпляру на
  каждого студента из списка `students`): отчёты, изменение темы, выговор, нормоконтроль,
  заимствования, отзыв и рецензия, допуск, защита, протоколы.
- **Развилки по уровню подготовки** (`level`): шаги, которые в каталоге есть только у одного уровня.
- **Контрольные точки** (необрывающий таймер → эскалация завкафедрой): `distribute_topics` (`topics_days`), `normcontrol` (`normcontrol_days`), `plagiarism_check` (`plagiarism_days`), `admission_order` (`admission_days`).
- **Дорожки = роли**: «Заведующий кафедрой» → `dept_head`; «Секретарь кафедры» → `secretary`; «Руководитель ВКР» → `supervisor`; «Нормоконтролёр» → `normcontrol`; «Ответственный за проверку на заимствования» → роли в системе пока нет; «Студент» → `student`; «ГЭК» → роли в системе пока нет.

## Отличия to-be модели от рабочей модели `vkr_defense`

- Рабочая модель — 7 шагов (`approve_topics`, `report_2`, `publish_for_normcontrol`, `normcontrol`, `publish_final`, `admission_order`, `defense`) на одного студента, со студентом как участником (дорожка «Студент», экран «Моя защита»); to-be — 29 шагов на выпуск с подпроцессом по студентам. Один экземпляр = один студент — это нужно для анализа журнала событий: case = траектория студента.
- В рабочей модели у предзащиты нет ветки «не прошёл → выговор», а контрольных точек с таймерами — 3 (`approve_topics`, `publish_for_normcontrol`, `normcontrol`).
- Эскалация в рабочей модели **прерывающая** (экземпляр завершается), в to-be — **необрывающая**: завкафедрой уведомляется, шаг продолжается. Прерывание в рабочей модели — упрощение ради измеримости эксперимента (глава 4), а не утверждение о реальном процессе.
- Календарные сроки каталога (месяцы, «за N дней до защиты») в to-be остаются в этой таблице; таймерами смоделированы только 4 контрольные точки. Абсолютных дат (заседание ГЭК) система не моделирует — то же ограничение, что описано в `experiment/params.py`.
- To-be исполняется оркестратором (`python -m orchestrator.tobe_smoke_test`), но в реестр ручного запуска не добавлена: в подпроцессе несколько READY-задач с одним именем (по одной на студента), а REST адресует задачу по имени — для запуска через UI нужна адресация по экземпляру задачи.
